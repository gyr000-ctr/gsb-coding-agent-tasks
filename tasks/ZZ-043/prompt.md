我们现在上线数据库改动全靠人肉数序号，谁先谁后写错了就炸；更麻烦的是有人回头改了已经上线的那个迁移文件，本地跟线上对不上也没人发现。想在这仓库里把迁移编排写出来。

入口一个 createMigrator，README 的《口径》和《API》两节把迁移怎么定义、校验和怎么算、执行顺序怎么排、已经有记录的那些怎么对账、跑一半炸了怎么回退、手动回退几条怎么算、每种错误报哪个码都写死了，照着来。目录里 lib/errors.js、test 下两组用例、scripts/demo.mjs 都已经写好，就差 lib/migrationplan.js，别的文件别动，也别引第三方包。

几个我特别在意的地方。执行顺序不是简单按 id 排：每一步都要在"依赖已经就位"的那些里挑 id 字典序最小的，所以 a 依赖 b、c 谁都不依赖的时候，顺序是 a、b、c，不是 b、a、c。校验和是从 up / down 的函数源码算出来的，改了函数体就等于改了校验和，plan / migrate / rollback 之前都要对一遍，对不上或者记录里的迁移已经不存在了都得当场拦住，但 status 不拦，它要把 applied、pending、drift、missing 四种状态都列出来。

失败回退这块最容易出事：默认只把"这一轮刚才跑起来的"按倒序退掉，之前就已经应用过的别动；失败那一条不能写进记录；如果回退的时候 down 也炸了，那要立刻停下，报出来的信息要说清是哪一条没退成、已经退掉了哪些、还剩哪些还是 applied 状态。选 stop 的话就干脆留在半路上不回退，但已经跑起来的那几条要留在记录里。

跑法两条：npm test 全绿（13 条，里面有依赖排序与同一步的次序、applied 与 pending、status 四种状态、漂移与缺失拦截、依赖未知与成环、定义校验、应用顺序与记录、跑过的不会重复跑、through 只跑一半、默认回退、stop 不回退、回退中 down 失败、手动 rollback 与条数校验、统计口径），npm run demo 的输出跟 README 最后贴的那段一行行对上。
