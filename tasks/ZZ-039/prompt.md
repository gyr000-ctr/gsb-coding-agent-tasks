我们的库最近老是卡住：一批事务互相等着，谁也走不了，最后只能人工去翻是哪几个会话卡在一块儿。想在这仓库里把"谁在等谁"的账记下来，顺便把死锁挑出来处理掉。

入口一个 createDeadlockDetector，README 的《口径》和《API》两节把事务怎么登记、要资源时什么时候直接拿到什么时候排队、释放时交给谁、等多久算超时、环怎么找、挑谁做受害者、每种错误报哪个码都写死了，照着来。目录里 lib/errors.js、test 下两组用例、scripts/demo.mjs 都已经写好，就差 lib/waitgraph.js，别的文件别动，也别引第三方包。

几个我特别在意的地方。队列是先进先出，释放的时候要交给最早排队的那个人，不能乱插队。每个事务最多只有一条等待边（它只等一个资源），所以环互相不相交——找环的时候从字典序最小的 txId 走，报出来的环也得从环里字典序最小的那个起按等待方向排，不然同一张图两次报出来的东西对不上。受害者的口径是环里最年轻的那个（startedAt 最大），并列时挑 txId 字典序更大的。

超时要严格大于才算（正好到点不算），而且一轮 detect 里先处理超时再看环——超时的那个被作废之后，它让出去的资源可能顺手就把环给解了。作废一个事务要把它等的那条边清掉、把它拿着的资源按 FIFO 让给下一个排队的人；被作废过的事务再来 wait 或 release 一律 ERR_TX_ABORTED。一个事务已经等上了还要等别的、或者去等自己已经拿着的资源，这两件事报的码不一样。

跑法两条：npm test 全绿（16 条，里面有先到先得、FIFO 排队的先后顺序、释放时的交接、环与受害者选择、多个环的排序、超时优先于环、单独设的超时额度、abort 之后的操作、被 abort 的事务交出资源、统计口径与各条参数校验），npm run demo 的输出跟 README 最后贴的那段一行行对上。
