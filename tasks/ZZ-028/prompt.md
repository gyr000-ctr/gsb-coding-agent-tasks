自研的 LSM 存储现在压缩是拍脑袋定的：哪一层先压、挑哪些文件、压完写多少，全靠现场看；
L0 文件可以重叠，往上层又不能重叠，墓碑什么时候能丢也不能乱丢。想在这仓库里把压缩计划
这块补出来，先把"该压哪一层、压谁、写多少"算清楚。

入口一个 createPlanner，README 的《口径》和《API》两节把层和文件的约束、配置与容量怎么算、
每层怎么打分、pick 怎么挑、L0 和 L1 往上的任务各怎么构造、maxInputBytes 怎么截断、
墓碑什么时候丢、写放大怎么算、每种错误报哪个码都写死了，照着来。目录里 lib/keys.js、
lib/errors.js、test 下三组用例、scripts/demo.mjs 都已经写好，就差 lib/planner.js，
别的文件别动，也别引第三方包。

几件我特别在意的事。L0 的文件本来就可以叠，但 L1 往上必须按 minKey 升序且两两不相交，
这个校验要做在前面，别算到一半才发现。打分口径要分清楚：L0 按文件个数、其余层按字节，
分数一样的时候先压靠下的层，最底层没有下一层就别给它派任务，哪怕它自己超了。

L0 的任务按 oldestSeq 从旧到新拿，累计体积不能超过 maxInputBytes，但至少留一个文件；
`to` 是下一层里跟这批文件合并范围相交的**全部**文件，别只挑一个。L1 往上的任务 `from`
只拿最左边一个文件，`to` 超上限时才退化成留体积最小的那一个，不然范围会漏。

墓碑只在压到最底层时丢，而且按文件算：size 减掉 tombstones × tombstoneBytes，不能为负；
压在中间层时一个墓碑都不能丢。outputFiles 是 ceil(outputBytes / targetFileSize)，
写放大保留三位小数，plan 顶层还要把各层的总量加总，没有任务时写放大是 0。
