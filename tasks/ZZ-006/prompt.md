我们订单中台一直有个老大难：大 key 一被打穿，几百个请求同时回源，库当场被拖死；上个月又出了
个更难受的，商品分类改了标签之后，有些实例还能读到旧数据，最后查出来是"失效之后才返回的那次
回源，又把旧值写回了缓存"。这两件事我想一起收掉，做成一个单独的读缓存层，仓库 ./cachegate
就是给这块留的位置。

骨架已经在里面了：共享存储的封装（线上是 Redis，这里把我们会用到的那几条命令一条条模拟出来，
都标了是不是原子的）、我们平时回源那层、计数器、配置解析、演示入口都在，用例也在，唯独
src/cache.js 里的 createCache 是空的，现在只会抛 not implemented。README 把接口签名、共享存储里
那几类 key 的名字、能用的命令、计数器叫什么名字都写清楚了，照着来；已有文件的接口、configs、
test 里的用例都别改，package.json 也保持现在这样。别装包，node 20 的标准库够用。

失效这条线是重点。谁能命中、谁不能，得看条目里记着的 tag 世代和共享存储里现在对不对得上——
别的实例刚失效过，你这边就不能再命中旧值。世代号只能往上走，两个实例同时失效同一个 tag、
同一个 tag 连着失效好几次，都不许回退，所以别写成读出来加一再写回去。还有回源途中被失效的
那种：回源之前就要把这次带的 tags 的世代取下来当快照，回源回来发现快照里的世代变了，这次结果
就不许写回缓存了（调用方拿到的值不变，照样给它）。反过来，回源跑完才去读一遍世代、把新世代
盖在旧数据上，是最典型的错法，这么写的人读侧会一直命中旧值，到 TTL 都出不来。

防击穿这块，同一个实例里同一个 key 的并发只准真回源一次，等着的那几个拿同一次结果（值或者
错误都一样）；跨实例靠共享存储上的锁，抢不到就退避回去重读缓存，别人写好了你就直接用。锁的
TTL 到了必须能被别人接手，不许把 key 锁死；释放锁得带着自己的 token 删，不能把别人正在用的
那把删掉——上次就是回源跑太久，锁过期给别人了，回来一通删，别人白锁了。token 要能区分开实例，
本地那个自增序号两个实例会撞成一个值。等超过 lockWaitMs 还没结果就自己抢一次，抢不到就直接
回源，宁可多打一次 origin 也不能把请求无限期挂那儿。

共享存储抖掉的时候按配置里的 failMode 走，fail_open 就直接回源（计降级），fail_fast 就抛
CacheUnavailableError；回源自己抛的错照常往上抛，别混在一起降级。还有回源已经成功、只是写
缓存那一步失败的情况，这次请求照常把值返回，别把好好的请求搞成 5xx，记一笔降级就行。loader 说
found: false 的写一条负缓存，TTL 内不要每次都去戳 origin，负缓存也得能被失效掉；回源抛错的时候
什么都不写，包括负缓存。计数器 README 里列了那几个名字，进请求、命中、没命中、真回源、回源报错、
失效、被栅栏拦下的写回、降级都要计上，我到时候就靠它看线上到底卡在哪一步。
