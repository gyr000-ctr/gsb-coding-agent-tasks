我们有批数据要放好几份，之前是各写各的，出了两次事故，这次想收成一层，仓库 ./quorumkeep
就是给它留的位置。

事情是这样：同一份数据我们会往三个副本上放，要求写出去的账在多数副本上落地了才算数；读的时候
也得问过多数副本，不能逮着一个副本就返回。上个月就是读到一个落后的副本，把一个已经改掉的值
又返回给客户端，对方拿着旧值把结算做了。另一回是网络抖了一下，两个协调者各自往不同副本写，
谁也不认识谁的版本，我们连着读到两个值，来回跳了好几天才查出根因。

骨架我已经搭好了：副本节点和集群传输层（延迟、掉线都在那层注入）、配置、计数器、错误类型、
HTTP 入口、演示脚本，还有 tests 下面的用例都在，现在红的。空的只有 quorumkeep/store.py 里的
create_store，现在调它会抛 not implemented。README 的《口径》写得比较细——版本向量怎么推、
两个版本怎么比、并发的两份写最后听谁的、读到旧的怎么修、超时怎么算、计数器叫什么——照着来，
别自己发明一套。已有的文件、配置、计数器名字、tests 里的用例都别改，也别引第三方包，
标准库够用。

我最在意的是这几件事。

读要凑够法定人数，凑不齐就明确报 quorum_unavailable，绝对不许拿手上唯一那个副本的值顶上充数。
写也一样，拿到足够确认才算成功；没写成功的那些副本留在那儿没关系，后面读的时候顺手修回来，
但别回滚已经写进去的数据。读修复只修那些答上来了、但手上不是最新的副本，没答上来的别去猜。

并发冲突必须收敛到同一个结果。两个协调者在互不知情的情况下写同一个 key，版本向量会互不支配，
这时候得有一套定死的取舍规则，让所有副本最后落到同一个值上。README 里给了比法，照那个来，
别用随机数或者遍历顺序。修好的副本要真的存住赢家那份，不能只在返回值里体现。

超时别用真实计时器。deadline 是你算出来传给传输层的，传输层按副本延迟判断来不来得及；
测试和演示塞的是手拨时钟，用 asyncio.wait_for 或者 time.time 在那边一点都不走，写了等于没写。
时间也只能从注入的 clock 拿。

做完怎么验：python -m unittest discover -s tests -t . 全绿；python -m quorumkeep.demo 的输出
跟 README 里贴的那段逐行对上；再起一次服务（python -m quorumkeep.server configs/dev.json 8090），
README 里那三个端点的行为照着对一遍。
