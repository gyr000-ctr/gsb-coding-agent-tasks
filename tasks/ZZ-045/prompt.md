备份那块磁盘一直不够用，想自己写个压缩把重复的部分吃掉。之前那版是别人随便找了个库糊的，
换个版本号压出来的字节就不一样了，两份备份没法比，出了坏块也说不清是被改了还是本来就那样。
这次想在这仓库里把打包和解包写出来，字节必须钉死。

入口三个 compress、decompress、checksum，README 的《口径》和《API》两节把头的布局、
标志位怎么排、匹配怎么编码、窗口多宽、长度上下限、挑匹配的规矩、解压时哪些情况算损坏、
每种错误报哪个码都写死了，照着来。目录里 lib/errors.js、test 下两组用例、scripts/demo.mjs
都已经写好，就差 lib/lzpack.js，别的文件别动，也别引第三方包。

几个我特别在意的地方。挑匹配那一段要一字不差：站在当前位置往前最多看 4096 字节，
窗口里每一个位置都是候选，最长优先、长度一样的时候挑离得近的，凑不满三个字节就老老实实
写字面量，也别去搞什么延迟匹配。距离和长度都只有那么几位，4096 和 18 就是硬上限，
贴着上限的那一档要能编也能解，超一格就得是另一回事。

解压这边我最烦的是"坏了还装作没事"。载荷读到一半没了、匹配想抄还没解出来的字节、
匹配会吐过头、原始长度已经够了后面还挂着尾巴、校验和对不上，这些都得当场抛 ERR_CORRUPT，
一个都不能糊过去。头部的原始长度要是被人改成了吓人的大数，也别真去分配内存。

跑法两条：npm test 全绿（15 条，里面有空输入、短输入全是字面量、重复串按上限切匹配、
长度相同时挑近的、窗口边界 4096 与 4097、大块重复的压缩率、同样的输入压两次一模一样、
文字与随机数据的往返、各种损坏与越界、入参不是 Uint8Array），npm run demo 的输出跟 README
最后贴的那段一行行对上。
