上周那起事故你应该听说了：合作方一个同步任务写错了循环，几分钟里把下游打穿。当时临时按来源 IP
数了个数顶着，结果对方换一批出口 IP 就重新从零开始，等于没限。这次想在入口做正经的准入，
仓库 ./slotgate 就是给它留的位置。

我们要的是按方法分开管：每个方法配一个并发上限，超出的请求排进一个有限的等待队列，队列满了直接
拒，别把内存堆爆。排队要按期限来——手上只剩几十毫秒的请求不该排在还剩两秒的后面；期限过了还
在队里等着的，趁早让它走，别一直占着位置等轮到自己。

骨架我已经搭好了：下游模拟件（延迟、失败、下闸都能注入）、配置、错误类型、HTTP 入口、演示脚本，
还有 src/test 下面的用例都在，现在红的。空的只有 Admission/AdmissionLanes.java 里的 create，
现在调它会抛 not implemented。README 的《口径》写得比较细——一次调用按什么顺序判、什么情况报
哪个码、超时值怎么取、排水怎么做、snapshot 每个字段什么意思——照着来，别自己发明一套。已有的
文件、配置、字段名、用例都别改，也别引新依赖，JDK 自带的东西够用。

几件我特别在意的事。

并发上限是硬的。我不管你内部怎么摆，下游同一时刻被调的次数不能超过配的那个数，用例会盯着下游
记录的最大同时在飞数看。许可也不能漏：下游超时、下游报错、请求被中断、排水，这些路径上许可都
得还回去，不然跑一阵子闸门自己就堵死了。

排队和期限要算清楚。排队的请求在等待期间也得盯着自己的期限，到点立刻出队报 DEADLINE_EXCEEDED，
不能等轮到我了才发现已经过期。真正去调下游的时候，超时值取剩余期限和这个方法自己的预算里较小
的那个——排队花掉的时间也算在这份预算里，别让一次调用在排队上耗掉一半、下游又拿到一整份超时。

停机要能排空。开始排水以后不再接新请求，队列里排着的也一并拒掉；在飞的让它跑完，grace 之内
排空了才算干净。这块我们吃过亏，上次是直接把进程掐了，客户端一片超时。

还有一条：下游只能通过传进来的那个 downstream 对象调，别自己起线程池绕过闸门把并发放大。

README 里贴的那段逐行对上；再起一次服务（--args="serve configs/dev.json"），README 里那三个
端点照着点一遍。
