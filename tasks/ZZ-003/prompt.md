我们对外有个写接口，最近被重试搞得很难受，想在这条路上加一层幂等，这块交给你。

事情是这样的：合作方调我们的接口，超时了它就自己重发；我们自己的网关重试、定时任务重跑，
也都会把同一个请求再打一遍。下游是真要干活的（写库、往外发通知），同一次操作进去两遍
就是真的做了两遍，月底对账的时候特别难看。合作方那边现在会自己传一个 Idempotency-Key，
同一次操作重发就带同一个 key，我们这边要认这个 key。

仓库 ./idemgate 是个 Node 骨架：HTTP 入口、配置、计数器、响应录制器都在，用例也在，唯独
src/idempotency.js 里那层是空的，现在只会抛 not implemented。README 把接口签名、指纹怎么算、
哪些头跟着回放、TTL 和几个上限都写清楚了，照着来；configs 里的配置、计数器的名字、
test 里的用例别改。别装包，node 20 的标准库够用，package.json 保持现在这样。

最要紧的是同一个 key 挤在一起的时候。只能真的执行一次，后面那些挂在这次执行上等结果，
别一个个都跑去执行——上周压测就撞见同一个 key 的五个请求一起进来，接口被打五遍，
下游实打实收到了五份。等的人太多也得有个上限，为这个把内存排爆就不值当了。

指纹别偷懒，方法、路径、请求体都要算进去。同一个 key 换了 body 就是另一件事，当场 409，
不许挂上去等，更不许把上一次的结果塞给人家——上个月出过这个事，合作方拿回去一份跟他请求
毫不相干的结果，我们查了半宿。还有网关会往响应头上撒一堆东西，回放的时候只回白名单里那几个
（content-type、cache-control、location、etag），set-cookie、date 这类别跟着回去，
content-length 按实际 body 重算。

结果要能原样重放：第一次的状态码和 body 都留着，TTL（毫秒）之内同一个 key 再进来直接回放，
handler 别再动了。缓存条目也得有上限，超了就把最久没用过的挤掉，不然这张表一天就涨到没边。
补充一句，某一次执行跑得比 TTL 还久的时候，等在它上面的请求还是要等它，
别因为时间过了就自己重新跑一遍。

handler 自己挂了、或者干脆没把响应写完，这种不算结果：发起的人和挂在上面的等待者都回 500，
而且这次别缓存，下次同一个 key 进来还得重新执行。客户端断开也遇到过：发起的那一端人走了，
等着的那一端还在——执行别跟着断，结果照常留着，写不回去就写不回去，计数器里记一笔就行。

计数器 README 里列了那几个名字，进请求、真执行、回放、等待、冲突、淘汰、断开、拒绝都要计上，
我到时候就靠它看线上到底是哪一步多打了。
