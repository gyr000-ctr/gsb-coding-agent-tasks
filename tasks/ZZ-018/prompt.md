想改成先写日志再改内存的做法，具体口径（帧格式、恢复规则、版本读法、checkpoint、错误码）
我都写在 README 的《口径》和《API》两节里了，是定死的。目录里 lib/codec.js（帧编解码）、
lib/log.js（只管字节的追加日志）、lib/errors.js、test 下三组用例、scripts/demo.mjs 都写好了，
就差 lib/store.js 里的 createStore，别的文件别动，也别引第三方包。

写到一半断电不能把数据搞坏。日志尾部那种半截帧恢复时必须不认，而且只丢那一帧，前面已经提交
的必须原样回来；日志中间如果校验不过（我们那块 eMMC 出过一次），从坏的那帧开始后面的就别
要了，但日志得截到能用的位置，别让后面接着写又写坏。恢复完之后开着的版本号要接着走，
不能倒回去。

没提交的事务一个字节都不能算数。我们的做法是 set 的时候就往日志里写，最后 commit 才算收尾，
所以恢复的时候必须靠 COMMIT 帧来认，日志里躺着的那种写了没提交的、或者提交前被杀掉的事务，恢复出来一律不能生效。

要能按版本读。审计要的是"昨天下午那一刻这个 key 是什么"，所以每个 key 的历史都得留着，
删除也要留墓碑，读的时候能给一个版本号。checkpoint 之后这些老版本也得照样查得到，
别 compaction 一把把历史抹平了。

checkpoint 得能真的把日志收小，顺序不能反（先写快照帧再丢前面的），中间断电恢复出来也不能出错。还有没提交的事务的时候直接报错，别糊里糊涂写个快照。

npm run demo 的输出跟 README 最后贴的那段一行行对上。
