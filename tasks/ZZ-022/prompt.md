我们发版脚本里那段"挑版本"的逻辑现在是拍脑袋写的，靠一个固定优先级表，一遇到两个包互相
顶就随便挑一个，装出来的树自己都对不上，半夜回滚过两回了。想在这仓库里重写一个正经的求解。

入口一个函数，README 的《口径》和《API》两节把约束怎么攒、按什么顺序挑包、挑不出来怎么退、
结果里那几个字段怎么算、每种错误报哪个码都写死了，照着来。目录里 lib/semver.js、
lib/registry.js、lib/errors.js、test 下三组用例、scripts/demo.mjs 都已经写好，就差
lib/resolve.js 里的 resolveDeps，别的文件别动，也别引第三方包。

几件我特别在意的事。一定是先挑满足约束的最高版本，走不通才往下退，退回来的时候上一层加过的
约束得干干净净撤掉，别把上一轮的残留带到下一轮去。同一个请求方对同一个包提的同一条范围
只能算一条约束，重复提不能把统计搞肿。

解不出来的时候别再只给一句"无解"了，运维那边要的是谁卡住、谁提的要求。chain 里那个 from
得从 root 往里排，root 自己提的排最前面，我们好顺着看是谁把谁逼死的。

钉住的版本要真的钉住，别看到更高的就又去挑高的；钉住的和约束打架就明说，不要悄悄改成别的。
成环的包我们也有，别在里头转圈。

跑法两条：npm test 全绿（21 条，里面有专门盯回溯、冲突链和钉版本的），npm run demo 的
输出跟 README 最后贴的那段一行行对上。
