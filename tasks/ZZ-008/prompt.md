先说背景，不然你写出来八成不是我想要的东西。

我们用户库里的手机号、身份证号一直是明文存的，这次安全那边下了整改通知，必须密文入库，主密钥
还要按季度换一次。我本来以为这就是个加解密的事，上周开会听他们讲了个别人家的事故，我当场就
坐直了：那家加密是加了，AAD 写成了一个固定字符串，后来有人在库上把密文从一条记录挪到另一条
记录，服务照样解得出来，一路没人发现，直到对账才对上。这种事落到我们头上就是大事，所以这回
不能只做到"能加解密"。

仓库 ./sealstore 是给这块留的位置。你先把 README 从头看一遍，我要的口径都在里面：keyring 怎么
读、记录落在磁盘上长什么样、AAD 拿什么拼、临时文件叫什么、计数器有哪几个、用例各在验什么，
都写了，别自己再发明一套。keyring、配置、错误类型、计数器、演示入口、test 下面的用例、
configs、keys 都是现成的，照着用，不要改；要你写的只有 src/vault.js，现在打开是空的，只会抛
not implemented。也别装依赖，node 20 自带的 crypto 和标准库够用，package.json 别动。

有两点我不放心，你重点看。一个是 AAD，得把记录 key 和列名都绑进去，谁把 A 记录的密文抄到 B
记录上、或者把 phone 的密文塞进 idcard，解的时候就必须直接失败；解不开的情况——包括 base64
都解不出来、长度不对那种——统一报 TamperError，别让 crypto 底层的错或者 JSON.parse 的错漏
出去，更别把明文和密钥打日志。另一个是轮换：rotate 把比当前版本旧的记录整条重写，已经是当前
版本的不许动，跑第二遍 rotated 得是 0。真正麻烦的是轮换和写入撞一起——我读到一条老记录、正
准备重写，这中间同一个 key 被人 put 更新了，那这次重写就得放弃，不能拿我手里那份旧的明文把
人家的新值盖回去。上次上线就是这个毛病，轮换跑完有人发现自己刚改的手机号又变回老的了。这种
算 conflicts，scanned 要等于 rotated + skipped + conflicts，我以后就看这三个数。

写文件别直接往目标上盖，先写临时文件再 rename 上去，进程被杀不能留半条记录、也不能把原来
那条好的毁了；临时文件叫 <key>.json.tmp-xxxx，别让它被当成记录扫到。key 只允许字母数字下划线
短横线、最长 64 个，带斜杠或者 .. 的直接拒掉。同一条记录并发写、读写撞一起，读到的要么是旧
的要么是新的完整值，不能是半个。

怎么算做完：npm test 里那组用例现在是红的，跑绿了再跑一次
node bin/sealstore.js --config configs/dev.json，README 里那段输出照着对一遍，对得上就过。
