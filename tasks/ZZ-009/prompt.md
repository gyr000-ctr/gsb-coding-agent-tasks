定时任务这块得换个做法，这周排查的三件事我一并说给你听。

周三晚上那个抓取任务，上一次跑了四十多分钟没结束，到点又开了一个，两个同时在写同一批文件，
第二天数据对不上。大前天运维对时把机器时间往回拨了十几分钟，有几个任务在拨完之后又把已经
跑过的时间点跑了一遍。还有夏令时那天：报表任务定在本地 02:30，可美国那边那天本地根本没有
02:30，旧脚本干脆没跑，客户早上拿到的是空的。

所以想请你写个调度器，就在手边这个仓库里（叫 tickwheel）。除了 lib/scheduler.js，
别的都是现成的：手动时钟（演示和用例就靠它把时间快进过去）、配置、计数器、错误类型、
演示脚本、test 下的用例。README 里写了 cron 支持到哪一步、时区怎么算、夏令时那两种边界
怎么办、到点之后怎么触发、stop 怎么收尾，按那个来，别改别的地方，也别引依赖。

几个我盯着的地方，你动手之前先想清楚。同一个任务不许重叠：上一次没结束就先跳过这一次，
记一笔账就行，不要排队——一排队的实际后果就是你以为跳过了，过后全补着跑一遍。夏令时
那两个晚上必须对：本地不存在的分钟顺延到之后第一个有的分钟，重复出现的那一分钟只跑
第一次；这两个我特意挑出来当用例了，别想着糊过去。时间一律从外面注入，实现里别自己写
Date.now、setTimeout，不然测试用假时钟推时间的时候，你那几处还是按真时间走。

还有一个是 stop。停掉之后不能再触发新的；正在跑的那次等它跑完，stop 的 promise 才给出
结果；重复调 stop 拿到的是同一个。用例收尾全靠它，收不干净会一直挂在那儿。

怎么验：npm test 现在是红的，写完要全绿；再跑一次 npm run demo，
README 里那段输出照着复现一遍。
