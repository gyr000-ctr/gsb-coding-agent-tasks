手上要个小表达式引擎：一段字符串进去，编成指令，再拿环境跑出结果。环境里没有现成的，自己写一份。

入口就 compile，出来的对象上要有 source、assembly 和 run(env)：assembly 是每条指令一行的字符串
数组，run 拿环境把值算出来返回。README 的《口径》《指令集》《API》三节是标准答案：认哪几种字面量、
优先级怎么排、三元从哪边结合、值只有哪四种、加减和比较判等的类型规则、假值有哪几个、短路时右边
算不算、文本化怎么写、除零和类型错各报什么码、环境里的名字找不到报什么、语法错的 details 里
index / line / column 怎么数、指令集有哪些、跳转目标是什么、优化器允许做哪两件事、哪些组合不许折、
CONST 的常量在 assembly 里怎么写，都写死了，照着来。目录里 lib/errors.js、test 下两组用例、
scripts/demo.mjs 都已经写好，就差 lib/exprvm.js，别的文件不动（用例是标准，别改用例去迁就实现），
也别引第三方包 —— 更不能把表达式转手丢给 eval 或者 new Function 去算，那等于没写（用例里会拿
两份 assembly 和错误码逐项对着比）。

容易写歪的地方：优化开着和关着必须等价，所以「会抛错」的常量组合（1 / 0、1 - "a"）绝不能在编译期
折掉，得原样留到运行时才抛；常量条件已经短路的那半边要整段消失，1 && x 折完只剩 LOAD x 一条（0 || x
也一样只剩 LOAD x，0 && nope 直接变成 CONST 0）；&& 和 || 返回的不是布尔而是操作数本身（0 && 2 是 0，
1 && 2 是 2，"" || "空" 是 "空"，null && nope 是 null）；比较和判等都要求两边同类型（"1" == 1 是
ERR_TYPE 不是 false，null == null 才是 true）；% 的符号跟被除数走（-7 % 3 是 -1）；拼接只要有一边是
字符串就走文本化（42 + "n" 是 "42n"，"x" + null 是 "x"，"-0: " + -0 里那个 0 不带负号）；名字大小写
敏感，true / false / null 是关键字不是变量；同一个 compile 出来的对象要无状态，连着 run 两次结果
一样；指令里的跳转下标是绝对下标不是相对偏移；两千项相加、五百层括号这种长表达式要能编能跑。

跑法两条：npm test 全绿（11 条，里面有算术与优先级、字符串拼接与文本化、比较判等的类型规则、
真假值与短路、三元与一元叠加、环境取值、语法错清单与位置、类型错与除零、折叠开关等价、指令序列、
入参校验与长表达式），npm run demo 的输出跟 README 最后贴的那段一行行对上。
