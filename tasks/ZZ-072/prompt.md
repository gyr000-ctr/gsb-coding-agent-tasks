排班那边要个「最早几点能到」的路由器：一张有向图，边上可能带封路时间窗，路口上还可能挂着转弯限制，
给个出发时刻，问最早什么时候能到、走哪几条边。环境里没有现成的，自己写一份。

入口就 createRouter({ nodes, edges, turns })，出来的对象上要有 route({ from, to, departAt })、edges()
和 stats()。README 的《口径》和《API》两节是标准答案：节点和边怎么声明、边长和限速怎么换成秒数、
封路区间怎么读（左闭右开、跨零点怎么表示、整天封长什么样）、碰上封路是原地干等还是绕道、
departAt 超过一天怎么算、转弯限制 no 和 only 各是什么语义、起点迈出去的第一条边管不管、
到达时刻一样时按什么挑 path、返回的 arrive / seconds / path 分别是什么、去不了给什么、
哪些情况是 ERR_BAD_ARGUMENT 哪些是 ERR_UNKNOWN_NODE、details 里各带什么，都写死了，照着来。
目录里 lib/errors.js、test 下两组用例、scripts/demo.mjs 都已经写好，就差 lib/routegraph.js，
别的文件不动（用例是标准，别改用例去迁就实现），也别引第三方包 —— 更不是让你把最短路随手糊一遍，
状态要是「到了哪个节点 + 从哪条边来的」，把点当状态的话转弯限制和干等都会算错。

容易写歪的地方：封路是左闭右开，开始那一刻进不去、结束那一刻就能进了；跨零点写成 [开始, 结束]
且开始大于结束，别顺手当成非法输入；[开始] 等于 [结束] 是整天封，[0, 86400] 也是整天封，
这两种边就永远用不了，得绕别的路，绕不过去才返回 null；等是「到了这条边的起点、发现封着就在原地等
到这段封路结束」，不是绕远路也不是照原速慢慢挪，几段封路首尾挨着就得跳完再看一遍；departAt 能超过
86400，判封路时按当天秒（取模）来算；从起点迈出去的第一条边前面没有边，任何 no / only 都管不着它；
转弯限制里的 via 跟 from 那条边的终点对不上时，这条限制就是挂着好看、永远不生效，不是报错；
同一个节点配不同的入边是两种状态，别拿一个点一份最短时间就把它合并掉；并列时比 path 的边 id 序列
字典序（前缀更短的更小，['a1'] 比 ['a1','a2'] 小，['a1','a2'] 比 ['z9'] 小）；返回的 path 每条边的
from 都得接得上上一条边的 to，也一定不违反转弯限制；seconds 是 arrive 减 departAt，把等的时间算进去；
edges() 返回的快照要改不动内部（closures 也得拷一份）；建个图要能反复问，问两次答案连 path 都得一样，
两个 router 之间也不能串味；两百个节点、几百条边、几十次查询要跑得动，别写成指数级枚举。

跑法两条：npm test 全绿（13 条，里面有基本最短路与返回形状、并列时的字典序、封路与等待、转弯限制、
起终点相同与不可达、随机图上跟简单路径对答案、三类入参校验、第一条边不受限制、封路边界与整天封、
edges 与 stats 和无状态、大图上跟朴素模拟对答案），npm run demo 的输出跟 README 最后贴的那段一行行对上。
