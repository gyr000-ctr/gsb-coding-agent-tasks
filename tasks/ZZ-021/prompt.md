我们那个"两边各改一份配置再合起来"的小工具，现在是拿 git 命令行套出来的，服务器上没装 git，
而且合出来的标记跟后台的解析器对不上，前端点"接受我们这边"经常整段错位。想自己在这仓库里
重写一个，把这块接过来。

出口就一个函数，README 的《口径》和《API》两节把段落怎么切、每一段怎么定、标记长什么样、
统计怎么数、什么情况报哪个错误码都写死了，照着来。目录里 lib/errors.js、lib/lines.js、
test 下三组用例、scripts/demo.mjs 都已经写好，就差 lib/merge.js 里的 mergeThreeWay，
别的文件别动，也别引第三方包。

几个我特别在意的地方。段落是按公共行切的，两处改动中间一行公共行都没有就得当成一段来看，
别一边取了我们的、一边取了他的，合出来是个谁都没想到的东西。一边删一边改也是冲突，被删的
那行照样留在 base 段里给人看。两边产出完全一样就别报冲突，我们 markdown 里这种情况太多了。

我们那份配置一万多行，别再写成整块两两去比，跑一次要等半分钟谁受得了。CRLF 的输入现在混
进来不少，行尾那个 \r 别当差异算，输出统一给 LF。还有 clean 那个字段，我说的是"有没有
冲突段"，不是"输出里有没有尖括号"——union 把两份都留下的时候它该是 false。

跑法两条：npm test 全绿（21 条，里面有相邻改动、删改冲突、还有一万多行那组），
npm run demo 的输出跟 README 最后贴的那段一行行对上。
