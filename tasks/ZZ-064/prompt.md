要做个去重的在线 UV 统计：每天几百万个值丢进来，只关心大概有多少个不同的，内存不能跟着涨。
想用 HyperLogLog，但寄存器别一上来就开满 2^p 那点字节——前几千个非零桶用稀疏的 (桶号, 值) 列表
就够，多到一定数量再换成稠密的定长数组。

入口就 createHll，出来的对象上有 add / count / registers / representation / merge / clone，
外面还导出 hashOf 方便对落位，README 的《口径》和《API》两节是标准答案：哈希怎么切（SHA-256
前 8 个字节、高 p 位当桶号、剩下的位从高位往低位数第一个 1）、一个桶只留最大值、稀疏什么时候
换成稠密、换过去还能不能回来、registers 不管当前是什么表示都要吐出完整长度的数组、估计那三条
公式（原始估计、线性计数、大基数修正）各在什么条件下用、merge 是逐桶取大不是相加、哪些参数错
报哪个码，都写死了，照着来。目录里 lib/errors.js、test 下两组用例、scripts/demo.mjs 都已经写好，
就差 lib/hllset.js，别的文件不动（用例是标准，别改用例去迁就实现），也别引第三方包。

容易写歪的地方：桶号是取最高位那几位，值是从剩下的位里从高位往低位数第一个 1 的位置（1 基），
数反了整份估计都是歪的；全 0 的尾巴是 64 - p + 1 而不是 0 或 64；一个桶只留最大值，同一个值加
第二遍要返回 0；稀疏换稠密的线是「非零桶个数超过 sparseLimit」，刚好等于不算超，换过去就不许再
退回稀疏；registers() 给的是拷贝，改它不能动到内部，而且稀疏表示下也要按桶号把值摆到正确下标；
count() 的三条修正是有顺序的，先算原始估计，再看要不要走线性计数（条件是估计值 ≤ 2.5m 且有 0
桶），最后才看大基数那个修正，别把顺序调了；merge 要就地把另一份并进来（逐桶取大），返回值是
"有没有寄存器被改大"，两边 precision 不一样是 ERR_PRECISION_MISMATCH，别当成参数错误。

大基数误差范围、clone 独立、precision 与 sparseLimit 的口径、merge 取大与返回值、精度不一致、
稀疏换稠密的时机与不丢值、转稠密后不回退、分批合并与一次性加完一致），npm run demo 的输出跟
