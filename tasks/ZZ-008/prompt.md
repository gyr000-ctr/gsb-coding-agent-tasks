上周下游重启那回你还记得吧？我们每个调用点自己建连接，下游一挂全卡在那儿，等它起来又被
我们自己的重连冲了一遍。这次想把连下游这件事收成一个池子，别再让每个调用点自己管连接。

池子我按想好的口径搭了个架子，要写的就是 src/pool.js 这一个文件，现在打开里面是空的，
createPool 只是个壳。真连下游的驱动、配置、计数器、错误类型、演示脚本，还有 test 下面
那批用例，都是我写好的，别动；README 里接口、字段、各种口径都写全了，以那个为准。
别引依赖，这台机器上 node 20 自带的东西够用。

有几件事我特别在意。一是上限：maxConnections 是硬的，池子里"建好的 + 正在建的"加起来
任何时候都不能破，包括好几个请求同时进来、连接还在建的那一小会儿。额度满了就排队，
先来先拿；排队等够 acquireTimeoutMs 还没轮到的要能自己退出去，退了就不能再占位置，
也不能过一会儿又把连接塞给它。队列本身也得有上限，排满了直接拒，别把内存堆爆。

二是回收。借出去的连接，调用方忘了还（try/finally 写漏了、handler 直接挂了，都见过），
过了 leaseTimeoutMs 池子要自己把它收回来，当坏连接销毁、补一条新的，不能一直挂着等。
这里有个坑：租约得认人——一条连接还回来之后很可能马上又借给了别人，上一次那张旧租约
到点，不能把这会儿别人手里的连接收走，也不能把已经还回来、正躺在池子里的那条销毁掉。
线上要是随机断连接，八成就是这个写错了，查起来要命。

三是归还和关池。还回来的时候调用方说这条废了、或者驱动那边已经断了，就销毁换新的，
坏连接绝对不能再借出去。关池的时候：新的 acquire 直接拒，排队的那几个也要被叫醒拒掉；
空闲连接关掉；正在别人手里的那条不硬抢，等它还回来再关；所有连接都关完了，close() 才能
回来，重复调 close() 得拿到同一个 promise。

池子自己那个定时扫描也要走注入进来的 now / sleep，别在实现里直接写 Date.now、setTimeout，
测试塞的是假时钟，直接写就跟没扫一样。
