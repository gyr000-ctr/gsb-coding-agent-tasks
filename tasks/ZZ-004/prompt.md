我们有个对外的 API 服务，请求进来以后要同步去调好几个上游——额度、画像、地址解析这些，
走的都是内部 HTTP。现在每个调用点自己写 fetch 加 try/catch，重试就是 for 循环打三次，
超时各写各的。上个月上游抖了一下，我们这边一堆调用点各重各的，把人家恢复的时间又拖长了
一倍；上周三那个 503 更难看，十个请求进去，日志里数出来打了三十多次，根本看不出来是谁在
重试、谁在等。

想收成一层。仓库 ./egressguard 是给这块留的位置，现在只有骨架：src/upstream.js 是真正把
请求发出去的那层（返回 {status, headers, body}，失败时抛 errors.js 里的 EgressError，
错误分类枚举已经定好了），src/counters.js、src/config.js 也是现成的，configs/ 下有配置，
test/ 下有用例（现在红的）。要你写的是 src/guard.js 里那个 guard.call()，现在只会抛
not implemented。接口签名、配置字段含义、错误分类怎么判、计数器名字 README 里都有，照着来；
已有文件的接口、configs 和 test/ 里的用例都别改。不装包，node 20 的标准库够用。

最要紧的是别再让“每一次尝试都拿一份完整超时”。一次调用的总预算是 budget_ms，重试、退避等待、
排队，全从这一份预算里扣。新起一次尝试的前提是剩余预算还够 attempt_timeout_ms，而且这次尝试
绝不能跑过总预算的截止时间；不够就直接拿最后一次的错误返回，理由标成预算耗尽。429 带
Retry-After 的也得先算账：等完这点时间如果已经不够再跑一次，就别等，直接失败，理由单独记一类。
退避按 README 里给的公式来，抖动要有。

重试挑着来：连接失败、尝试超时、429、502/503/504 才值得再来一次；其它 4xx 是人家明确告诉你
不行，重试没意义。非幂等的（POST/PATCH/PUT/DELETE）默认不重试，除非调用方在这条请求上明确标了
idempotent，GET/HEAD 当幂等看。这条是真被坑过，一个 POST 重试出去，下游多扣了一次额度。

熔断按上游名各算各的。窗口是最近 window_size 次，样本够 min_samples 且失败比例到 failure_ratio
就打开；打开期间不再往上发，直接快速失败，快失败也得在计数里看得到。冷却到点进半开，这期间
只放 probe_concurrency 个探测进去，其它照样快速失败——冷却一到就把攒着的几十个请求全放进去，
等于没熔断，这种事见得太多了。探测成功 probe_successes 次才关闭并清空窗口，探测挂一次就立刻
回到打开，冷却按连续打开次数往上翻，封顶在配置里，成功关闭后重置。窗口记的是真实尝试：每一次
真发出去的尝试算一个样本，连不上、超时、429、5xx 算失败，上游给了 2xx/3xx/4xx（429 除外）
算成功；被熔断挡下、被队列顶回去、预算不够没发出去的，都不算上游的账。

同一个上游同时在飞的请求不能超过 max_concurrency，超了就排队，队列最多 queue_limit 个，
排不下立刻失败，别把内存堆爆；排队等的时间同样吃那份总预算。这条和熔断是一起的：别让一次
上游抖动被我们自己的背压放大成永久熔断。

时间和随机都不许直接用：now、sleep、random 三个从外面注入（形状 README 里写了），实现里
不许出现 Date.now、setTimeout、Math.random。测试会塞一个假时钟进来，整个调用过程在假时间里
必须完全确定，也不能真的睡。

计数 README 里列了要记的那几个（进调用、真发出去的尝试、重试、预算耗尽、Retry-After 放弃、
熔断拒绝、排队、排队超限），再给一个 snapshot()，按上游给出当前状态、在飞数、排队数和这些
计数——线上出问题我就靠它看是哪一步多打了。

交付：npm test 里那组用例现在是红的，做完要全绿（预算耗尽、Retry-After 超预算、错误分类、
熔断打开→半开→关闭、半开探测并发上限、排队超限、快照这些都在里面）；再跑
node bin/egressguard.js --config configs/dev.json，README 里那段演示输出要能照着复现。
