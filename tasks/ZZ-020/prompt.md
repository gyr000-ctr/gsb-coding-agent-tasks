我们有个内部的知识检索小工具，现在是每次查询都把所有文档的正文拼起来做一次 includes，
文档一多就卡，而且排序基本靠写死的权重，客户老说"想找的东西不在第一条"。

想换成正经的倒排索引：文档丢进去，按词项查、按短语查、按字段查，分数要讲得清楚。
口径（文档形状、查询语法、打分公式、错误码）我都写在 README 的《口径》和《API》两节里了，
是定死的。目录里 lib/tokenize.js（分词）、lib/errors.js、test 下三组用例、scripts/demo.mjs
都写好了，就差 lib/index.js 里的 createIndex，别的文件别动，也不引第三方包。

几个我特别在意的点。

短语得真按位置算。我们搜"release notes"的时候经常把"notes on release"这种也捞出来，
这次必须相邻才算命中，而且不能跨字段拼。前缀查询是运营常用的（记不住全称），展开出来的
词要合起来当一个词项算分，别一个词一个词加。

分数要能对得上表格。文档长度、词频、命中多少篇文档这几个因素都要体现出来，公式 README 里
写死了，公式里的字段范围也跟着查询走（写了 title: 就只在 title 里数），算完保留 6 位小数。
分数一样的时候按 id 排，别让两次查询顺序不一样。

删文档不能留垃圾。我们每天都会重建一部分内容，删掉的文档再查不能出现，而且它的词要从倒排
里真摘掉：全删完的时候统计得是干净的零，不然跑几个月内存就下不去了。

查询写坏了要报错，别猜。比如字段名写错、引号没关上、星号放在词中间、|| 一边是空的。
还有中文：我们文档里中英混排，中文没加引号也得能用。

跑法两条：npm test 全绿（20 条，里面有拿 README 的公式自己算一遍来核对分数的），
npm run demo 的输出跟 README 最后贴的那段一行行对上。
