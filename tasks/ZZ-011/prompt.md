想把我们现在那个共享缓存换掉，自己写一个，仓库是 kvjournal。

背景是这样：上游几个服务都拿现成的 redis 客户端连它，所以协议得按 RESP 那套来，不然客户端连不上，
还得挨个去改那些服务。已经跑着的那条路上出过两次事：一次是有人发了一条超长的命令，进程一口气把
三百多兆攒在内存里；另一次是机器被人直接断电，重启之后最后几条已经回过 OK 的写没了，对账对到半夜。

仓库里 TCP 那一层、配置、计数器、错误类型、一个小客户端和演示脚本都在了，就差两块：
lib/protocol.js 里的请求流解析和回复编码，lib/store.js 里的内存表加日志。README 的《口径》把
帧格式、内联命令、超长了怎么办、日志里每条记录长什么样、重启之后尾巴上没写完的那条怎么处理
都写死了，照那个来。别的文件、configs、test 下的用例和那三份日志样本别动。仓库不引三方包，
标准库够用，package.json 保持原样。

几个我比较在意的地方。

协议这块，一条命令会被 TCP 切得七零八落，也可能一次来好几条，所以得能把半条攒着、把攒好的按顺序
交出来。长度是字节数不是字符数，我们 key 和 value 里中文不少，按字符长度算一定会崩。太长或者格式
歪了的输入要当场认定是坏输入：报错、别继续往内存里攒，服务端那边会把这条连接关掉。认不出的命令
只回个错误、连接别断——运维手抖敲错一个字母就掉线，这个受不了。

日志这块是重点。写命令必须先追加到日志、fsync 落盘，然后再回 OK，回过 OK 的就不能丢。反过来，
进程被 kill -9 的时候最后一条可能只写了一半，这种尾巴要能认出来丢掉，而且丢掉之后得把文件截到
最后一条完整记录的位置——不截的话下次接着写，后面那条就变成垃圾了，这个坑我们踩过。还得把
"尾巴没写完"和"中间坏了"分开：声明长度超过上限、内容不是合法 JSON、op 认不出来的，属于后者，
要报错，不能猜着往下读。

还有关停：收到信号之后不再收新连接，已经在处理的那几条命令要答完再退，不能丢掉已经答应的写。

跑法两条：npm test 全绿（里面有一条是真起一个服务进程、写一条、kill -9、再起来看数据在不在，
那条也得过）；npm run demo 的输出跟 README 里贴的那段逐行对上。
