我们网关这边上周出了个事，得在入口补一层限流。

起因是合作方一个同步任务写错了循环，几分钟里把下游打穿了。当时临时按来源 IP 数了个数顶着，
结果对方换一批出口 IP 就重新从零开始，等于没限。这次想按正经的维度来：整个网关一份总量，
每个调用方一份（请求头 X-Client-Id，没带就归到 anonymous），每条路径一份，三层都有名额才放行。

仓库我已经收拾干净了，configs/dev.json 里三层额度都配好了。lib/limiter.js 你打开看，
createLimiter 现在是个空壳，就等你写这一块：接口长什么样、每个字段什么意思、计数器叫什么、
什么情况算超限，README 的《口径》里都写清楚了，照那个来。config.js、counters.js、errors.js、
server.js 还有 configs、test 下的东西别动。仓库不引三方包，标准库够用，package.json 保持原样。

有几点我盯着，你动手之前先想清楚。

窗口要按滑动窗口算，不能整分钟一清。上一版就是固定窗口，结果一分钟的最后几秒打满、下一分钟
开头又满血，实际放出去的是额度的两倍，这次不能再这样。边界也得站得住：正好到点的、还差一毫秒的，
用例里都有。

被拒的时候要告诉调用方到底等多久，而且得是真正能过的时间。别只报最早能恢复的那一层——三层都
得有位置才放行，报早了对方照着重试还是被拒，白打一轮。还有一种情况：额度被压低之后，窗口里可能
堆着好几条，这时候不是"等最老那条过期"就够了，得等攒够条数过期才腾得出名额。这两条都踩过，
用例里专门有。

调用方和路径都是外面传进来的，不能来一个建一个，得有个上限，满了先挤掉最久没用过的那个；
被挤掉的那个调用方相当于重新开始，这个我认。但正在被打的 key 不能被别人顺手挤没了。判定也不许
退化成每次遍历整张表，用例里有 2 万次请求那一条，现在这台机器上跑一遍是毫秒级的。

另外配置是要能热更的（applyConfig）：换额度的时候窗口里已经攒下的计数不能清掉，抬了立刻能过、
降了立刻开始拒；配置不合法就当场抛错，旧的那份继续用，不能换一半。

时间别自己取，now 从参数里拿，测试塞的是手动时钟。跑法两条：npm test 全绿；
npm run demo 的输出跟 README 里贴的那段逐行对上。
