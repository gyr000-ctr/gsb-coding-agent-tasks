网关这块我想在评审前跟你先对一下，免得评审会上再掰扯一遍。

起因不复杂：我们对外的接口，合作方超时就自己重发，同一笔请求一秒钟能打到我们八次；反过来我们
自己也没做好，中间转发的时候有人改过 body，拿着原来的签名照样过去了。所以想在这条路上加一层
请求签名校验。算法和时间窗都是跟合作方谈定的，不是我们单方面定规矩，规范串 README 里写着，
你照着实现，别自己重新设计一套。

./signgate 这个仓库里，规范串和签名算法、密钥表、共享存储的模拟、HTTP 那层、计数器、错误类型、
配置解析、演示入口、还有用例，都现成，照着用，别改；空的只有 src/verifier.js 和
src/nonce-store.js，现在是抛 not implemented。README 写得比较细——五个头叫什么、规范串那七行
长什么样、每一步失败报哪个 code、nonce 的 key 怎么拼、计数器有哪几个——先看完再动手。不用装包，
node 20 标准库够。

我最担心防重放这块。线上网关是好几个实例一起跑的，nonce 都放在共享存储里，谁都不能靠本地内存
把事情办了——先查一下再写是最典型的错法，五十个请求同时进来会一起读到"没有"，然后一起放过去，
我在别的服务上亲眼见过一次，最后是靠对账才发现的。认领要用共享存储里那条原子的命令。还有个
顺序问题你千万注意：签名没验过之前，不许去认领 nonce。合作方是同一秒里批量发的请求，要是乱
签名的请求也能把 nonce 烧掉，他们真正那批就全被我们拦成重放，两边一起排查到半夜。

共享存储是惰性过期的，过期的东西不会自己消失，得有人去删，所以认领之前先整理：清掉已经过期
的，剩下的如果已经到 maxNonces，就从最旧的开始淘汰，别让人构造一堆随机 nonce 把内存撑爆。
被淘汰的那些再来我当它新的，这个我认；但刚用过的那条必须还在，重放照样得拦住。

还有个容易忽略的：时间窗的边界。差超过 windowMs 才算过期，正好卡在边上要放行——有家合作方的
机器时钟慢几十毫秒，卡边就拒的话他们天天来找我。错误码也要分清楚：头缺了、keyId 不认识、密钥
停用、body 摘要对不上、签名对不上，各报各的，别都塞成一个 400，我排障全靠它。比签名用
timingSafeEqual，长度不一样或者根本不是 hex 的直接判不过，别让 crypto 抛的错冒到外层变成 500。
计数器 README 里列了名字，通过、被拒、每种拒绝各一笔都计上，rejected 等于各分类加起来，这个
数月底对账要用。

README 里那段输出照着复现一遍就行。
