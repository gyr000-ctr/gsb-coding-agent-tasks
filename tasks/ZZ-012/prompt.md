我们计量这块一直是个手工活，这次想收成一个服务，仓库 ./meterroll 就是给它留的位置。

背景是这样：上游把用量事件打给我们，一条事件就是"某个租户用了多少"。超时重发、网关重试、
离线补传，都会让同一条事件进来好几遍；事件带的时间是它真正发生的时刻，可补传上来的时候
往往已经过了好几个周期。之前这套是拿定时脚本扫库算的，出过两次事。一次是重试的请求一起
挤进来，同一条事件被记了两遍，月底对账差了一截。另一次是某个周期已经出过账了，后来补传的
事件又被打进去，账目自己变了，对账的人查了三天才定位到。

骨架我已经搭好了：HTTP 层、配置、计数器、错误类型、H2 的存储封装（建表语句和事务助手都在），
test 下面的用例也在，现在红的。空的只有 Metering/UsageMeters.java 和 Settlement/Settlers.java
这两个工厂，现在调它们会抛 not implemented。README 的《口径》写得比较细——周期怎么切、重复
投递算什么、迟到按什么判、结算怎么幂等、加锁有什么讲究、计数器叫什么——照着来，别自己发明
一套。已有的接口、表结构、配置、计数器名字、test 里的用例都别改，也别引新依赖（H2 和 gson
已经在 build.gradle 里了）。

我最在意的是几件事。

一条事件只能算一次。同一个 eventId 投两遍、八遍都行，数字只能加一次，八个线程同时投也是这个
结果。这里有个坑：先查一下再插是最自然的写法，但并发下八个请求会一起查到"没有"，然后一起插
进去，这就是我们上次差一截的根因。

已经出过账的周期不许再被改。判定迟到只看一件事：那一期的结算记录是不是已经存在，跟时间差
多久没关系。已经结算的周期，后到的补传事件按配置要么结转到抵达的那一期、要么直接丢掉，
两条路都不许回头去动那一期的累计量。结算本身要幂等：同一个周期结两次，第二次得把第一次那份
原样还回来，数字一个字都不能变，哪怕中间又来了新事件。空周期也要能结，出来是 0。

并发下不能丢也不能双计。事件行、迟到记录、累计数字是一个事务，累加要用库里原地自增，
别读出来加完再写回去。迟到判定得在事务里、并且锁住相关的行之后再做，先判定后加锁会跟并发
结算打架，把事件塞进已经出过账的周期。要同时动两个周期的时候按周期起点升序加锁，别写出死锁。
usage_rollup 的行有可能还不存在，先保证行在再锁；两个事务同时补同一行会撞主键，捕获冲突重试
就行，重试要有上限，超了报存储错误。顺带说一句，H2 不允许 SELECT COUNT(*) ... FOR UPDATE，
要锁就选真实列。

时间别自己取，实现里从传进来的 Clock 拿，测试塞的是固定时钟，直接写 System.currentTimeMillis
跟没写一样。

做完怎么验：gradlew.bat test 全绿；gradlew.bat run --args="demo configs/dev.json" 的输出跟
README 里贴的那段逐行对上；再起一次服务（--args="serve configs/dev.json"），README 里那四个
端点的行为照着对一遍。
