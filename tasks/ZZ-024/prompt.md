权限那块现在是一堆 if/else，每接一个客户就得改代码，改完还老有人问"为什么他能看我不能看"。
想在这仓库里写个属性化的策略引擎，把判断挪到配置里去。

入口一个 createEngine，README 的《口径》和《API》两节把属性怎么继承、策略怎么匹配、
条件怎么判、优先级和拒绝谁说了算、缓存什么时候清、每种错误报哪个码都写死了，照着来。
目录里 lib/conditions.js、lib/errors.js、test 下三组用例、scripts/demo.mjs 都已经写好，
就差 lib/engine.js 里的 createEngine，别的文件别动，也别引第三方包。

几件我特别在意的事。主体和资源的属性是叠出来的：角色先铺一层，本人的 attrs 盖上去，
别把顺序搞反了，不然"这个人比角色高一级"这种就判不对。

结论这块，优先级高的先说话，同一个优先级里 deny 必须赢——我们宁可拦错也不能放错。一条都
没命中的时候是默认拒绝，别手一抖给了 allow。obligations 要原样带出来，下游全靠它决定
打不打码。

运维最烦的是"为什么"，所以 explain 得说清楚每条策略为什么算、为什么不算，条件不过是指到
具体哪个路径，属性压根没有的时候也要能看出来是缺东西。缓存是给高频判定省事的，换策略或者
换属性表的时候必须清干净，不能让旧结论接着用；explain 别走缓存，每次现算。

跑法两条：npm test 全绿（21 条，里面有专门盯优先级、同档拒绝优先和缓存失效的），
npm run demo 的输出跟 README 最后贴的那段一行行对上。
