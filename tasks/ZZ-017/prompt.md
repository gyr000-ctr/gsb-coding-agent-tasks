规则、字段、错误码、返回的字段名我都写在 README 的《口径》和《API》两节里了，是定死的。
目录里 lib/ics.js（规则解析和校验）、lib/tz.js（墙钟和时刻互转）、lib/errors.js、test 下三组
用例、scripts/demo.mjs 都写好了，就差 lib/expand.js 里的 expandSeries，别的文件别动，
也不要引第三方包，Node 自带的就行。

展开要在本地日历上做。也就是说"每周日 09:00"这种，跨过夏令时之后本地钟点还是 09:00，
UTC 时刻自己挪；别拿 UTC 每七天加一次那么算，那样跨夏令时的钟点就漂了。窗口筛选、
COUNT 和 UNTIL 的判定都别破坏这个语义。

夏令时那两档必须分清楚。春季跳表那一小时里的墙钟压根不存在（纽约 2026-03-08 凌晨 02:30），
这种按跳表之后的偏移往后挪；秋季回拨那一小时出现两次（纽约 2026-11-01 凌晨 01:30），
取先发生的那次。落在哪一档要能从结果里看出来，我们前端要拿这个跟运营解释。

按月的规则别自作聪明。每月 31 号的，二月、四月这种没有 31 号的月份就跳过，不要顺延到
下个月 1 号；每月最后一个周五、每月最后一个工作日（BYSETPOS=-1）这两种我们也用得很凶，
得算对。周怎么切是按 WKST 来的，我们把 WKST 当配置项给客户，切法不同结果会不一样，
这个别写死了。

例外和改期都要支持。EXDATE 去掉的那次不能再产出，但它照样算 COUNT 的一个名额，
不能因为少了一次就多展开一次补回来；RDATE 是额外加的发生；override 按原始那次的墙钟
匹配，可以改开始时间、改时长，也可以整个取消；override 匹配不上任何一次说明上游数据
脏了，要报错别吞掉。

输出按开始时刻排好序，序号从 1 连着编，别跳号。结果条数有上限，展开停不下来也要拦住。

跟 README 最后贴的那段一行行对上。
