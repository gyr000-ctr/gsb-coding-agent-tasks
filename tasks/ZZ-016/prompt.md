我们那个上传接口想换一套分片续传的做法，先把背景说一下。

现在客户端是把整个文件攒在内存里一次性 POST，地铁上网一断就得从头上传，客服天天被骂。
上个月更麻烦：运维找上门说对象存储的账单不对劲，同一批报表文件内容几乎一样，我们却按份
存了好几遍；还有一次客户端把同一块传了两遍，服务端当成新内容又收了一遍，最后拼出来的
文件多了几个字节，用户下下来是坏的。加上服务重启过一次，几十个传到一半的会话全丢，
用户只能从头再来。

想做成一个会话引擎：分片收，能去重，能续传，能验货。错误码、事件、上限这些我都写在
README 的《口径》和《API》两节里了，是定死的，照着来。目录里 lib/errors.js、lib/hash.js、
lib/blobstore.js、test 下的三组用例、scripts/demo.mjs 都已经写好了，就差 lib/relay.js 里的
UploadRelay，别的文件别动，也不要引第三方包。

有几件事我特别在意。

拒绝要快。长度不对、hash 不对的片子，在"确认这堆字节就是这一片"的那一刻就该拒掉，
不能先把字节塞进存储、等拼完整文件再回头发现不对；被拒的片不能留在会话里，也不能算进
已收字节，客户端重传一片好的就行。

去重得按内容算，引用数也得真的数住。内容一样的片只存一份字节是基本要求，但引用清零的
时候必须真把字节删掉，不然存储只会一路涨。同一片重传同一份内容算幂等成功，别报错；
同一片换了一份内容才是冲突，保留先收到的那份。

进程重启不能丢数据。我打算把会话状态定期落盘，所以引擎得能 snapshot 出一个普通对象
（能 JSON.stringify 的那种），新进程 restore 回来接着收片、接着收尾，事件序号和自动
生成的上传号都要接着数，不能重号。

不要一直攒着。收片过程中除了这一片的字节和该存的 blob，不该再留别的常驻内存；没人管的
会话、过了保留期的完成会话得能被 sweep 清掉，字节一起放掉，清出来的字节数要能对上。

跑法两条：npm test 全绿（25 条，其中一组专门盯事件顺序和统计，一组是重启后接着传），
npm run demo 的输出跟 README 最后贴的那段一行行对上。
