我们售后和交付的同学老在客户现场干活，机房和园区里没网，内部 wiki 打开就是转圈。
手头这堆手册全是纯文本和 markdown，平时想找一句话只能一篇一篇开，翻半天。
想做个网页版的小检索页，把手册都丢进去，本地就能查，全程不联网。

语料我导了一份在 samples/corpus 下，几十篇，怎么放怎么命名看 README，别改。
另外 samples/queries.json 是我攒的查询用例，每条写了查什么、该命中哪篇文档哪一段的哪几个字。
这就是验收标准，跑完要能逐条对给我看；哪条不对，要指名道姓说清是哪一条。

先说中文没空格这事。我们手册里"风控策略灰度"这种词中间是没有空格的，
按空格切词的做法一定查不到，你得自己想个办法，双字切、前缀、带权都行，随你。
英文大小写不敏感，全角半角得当成一回事，查询词收尾的空格和标点别算进去。
短语查询要连续命中，不能拆成两个词各中一次就糊过去；前缀查询要能补全，
输入"回滚步"得命中"回滚步骤"。

结果得落到实处：哪篇文档、哪一段、段里第几个字到第几个字，点一下跳到原文并把那一处标出来。
我要看到命中的到底哪几个字，不接受整段高亮。区间按 Unicode 码点算，
别拿 UTF-16 长度凑——文档里有 emoji 和生僻字，上次按字节切把标点都切碎了。

索引要能增量重建。手册一年改几十次，我不想每次都全量重来：给我一批新增和改过的文档、
再给我一批删掉的，索引得跟着变，删掉的必须再也查不到。重建要真的比全量快，
页面上把两次的耗时都打出来给我看。更新那批按 samples 里的写法来。

还有性能。我们最大的一份语料三万多段，samples/stress 里的生成器就是按这个量级造的，
索引构建完页面不能卡死，单条查询要在 300 毫秒以内，你打的耗时我能看见；
连着查几十次内存别一路往上涨。结果排序要稳定，同一个查询连查两次，顺序必须一模一样。

README 里写清楚你的分词和归一化规则、索引结构、增量重建怎么判断、
排序怎么定、码点区间怎么算，还有自检怎么跑——我想点一下、或者一条命令，
就能把 queries.json 全跑一遍，通过的、失败的分开列出来。

别引库别 npm 别构建，原生 ES module，我 python -m http.server 开，别联网别调接口。
