我们内部的事件推送网关最近连着出洋相。上周一个大客户那边读得慢，事件全堆在网关里，内存撑到
8G 被 OOM 杀掉；还有个客户端断线重连之后丢了一段事件，反馈过来我们连缺了哪几条都说不清；
再往前还有人投诉，同一批事件收到的顺序跟发布顺序对不上。这块我想重写，仓库 ./eventpush 就是
给网关留的位置。

骨架已经在里面了：HTTP 那层（GET /events 走 SSE、POST /publish 发事件）、帧的编码、计数器、
配置解析、演示入口都在，用例也在，唯独 src/hub.js 里的 createHub 是空的，现在只会抛
not implemented。README 把接口签名、帧长什么样、配置字段、计数器名字都写清楚了，照着来；
已有文件的接口、configs、test 里的用例都别改，package.json 保持现在这样。别装包，node 20 的
标准库够用。

最要紧的是别让慢客户端把我们搞死。每条订阅有自己的队列，上限就是配置里那个 perConnBuffer，
满了按这条订阅的 overflowPolicy 走：drop_oldest 就丢队列里最旧的一帧，disconnect 就直接把这条
订阅断掉。正在发的那一帧不算在队列里，别把它也丢了。publish 只负责把帧塞进队列，绝对不许等
客户端——一个读得慢的人不能把 publish 卡住，更不能拖累别的订阅者收事件。发送循环每发一帧，
send 返回 promise 就等它，send 抛错或者 reject 就把这条订阅断掉。

顺序和补发是另一条线。seq 全局单调递增，从 1 开始，在 publish 被调用的那一刻就分配好，先调的
号小后调的号大，中间不能因为 await 插队乱序；一个客户端收到的事件的先后必须跟发布顺序一致。
断线重连的客户端会带 Last-Event-ID，你要从保留窗口里把 seq 大于它的、它订阅的 topic 的事件
按原顺序补一遍，每条只补一次；补发跟实时事件走同一条队列，补发的先排进去，所以补发期间新发的
事件要排在补发后面，不能插到中间也不能重复。要是 lastEventId 比窗口里最老那条还老，说明中间
已经缺了一段，先发一帧 event: replay_gap 把 requested 和 oldest 说清楚，再把窗口里有的补上，
别装作补全了。窗口本身是有限大小的，越界的从最旧那头丢。

关停也别糊弄。close 之后不再收新订阅、publish 当场拒掉（不能悄悄丢事件），已经在队列里的事件
要写完，每条订阅最多等 drainTimeoutMs，等不到就断开它并记一笔；所有订阅处理完了 close 才能
回来，重复调用直接返回同一个 promise，跟 publish、subscribe 撞在一起也不许死锁。订阅总数超过
上限的、关闭之后还想订阅的，都要当场拒掉并计数。时间和随机都从外面注入，实现里别直接写
Date.now、setTimeout，测试会塞假时钟进来看 drain 和补发这两步。计数器 README 里列的那几个
名字别改，发布、真送出去、丢弃、断开、补发、补发缺口、被拒的订阅、被拒的发布都要计上。
